# ADR-0005: Scryer integration strategy

Status: Proposed. To be confirmed by a Phase 3 spike.

## Context
PRD §20–§25: Rust owns the infrastructure, and Prolog must do a *meaningful*
part of the procedure, at least dilemma branch exploration. These are the
verified API constraints (feasibility report §3.3):

* queries are strings;
* there is no Rust callback from Prolog;
* `Machine` is not `Send`;
* exceptions poison the machine unless caught;
* there is no resource-limit API.

## Options
1. **Prolog runs whole branches.** Rust parses, decomposes, runs the root
   0-saturation and drives the top-level k loop and the merges. For each branch
   Rust calls Prolog with `execute_branch(State, Assumption, K−1, Result)`, and
   Prolog performs the branch-local `sat_{k−1}`, including any nested
   dilemmas. This mirrors PRD §22's interface.
2. **Prolog runs all saturation.** Rust only parses, decomposes, consults the
   triples as facts and reads back the canonical result. This minimizes
   boundary crossings, but Rust's role is close to trivial.
3. **Prolog runs only dilemma control, and Rust runs the 0-saturation.** This
   is impossible: there is no callback API.

## Decision (proposed)
**Option 1 is the primary design.** Option 2 is a controlled experiment
(PRD §25.6).

* **Loading:** triples are consulted once per formula as facts:
  `t(Id, Kind, X, A, B).` and `occ(Node, [TripleIds])`. The SPEC-S1 local
  closure table is generated by Rust from the normative definition and consulted
  as `rule(Kind, Shape, Pattern, Result)` facts, so both sides share one
  source of truth.
* **State exchange:** a branch's parent state is sent as a compact canonical
  term. It contains only non-singleton classes, as a list of `Min-[V-P,…]`
  pairs. The branch result returns the same shape, or the atom
  `contradiction`. Prolog keeps the state in `library(assoc)` (persistent AVL),
  so nested branches share structure (Strategy C).
* **Query hygiene:** every query has the form
  `catch(stal:execute_branch(...), E, (R = error(E)))`. Iterators are always
  drained. Queries are built by one formatter, which is property-tested to emit
  parseable Prolog.
* **Lifecycle:** one `Machine` per solver run, reused across branches. A fresh
  machine per branch is the PRD §25.1 experiment. Parallel branches would need
  one machine per worker thread, built on that thread.
* **Limits:** Prolog code threads a step budget and returns `limit(Which)`
  when the budget runs out.
* **Instrumentation:** separate timers for query building, Prolog execution,
  and term decoding.

## Consequences
* Boundary cost per branch is O(size of non-trivial state). This is exactly
  what PRD §24 asks to be measured.
* The 0-saturation rules exist twice (Rust and Prolog), so differential tests
  (P5, P6) must cover branch results directly, not just final answers.
* Revisit this ADR if a host-callback API appears in a later `scryer-prolog`
  release.
